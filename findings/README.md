# Cyber-Tiel-Coder-35B-A3B MTP on Jetson AGX Xavier - findings index

**Updated:** 2026-11-08
**Goal:** maximize generation speed at a 262,144-token server context, retaining MTP and full
target-model GPU offload; discard measured configurations below 23 tok/s.

This directory replaces the old single `FINDINGS.md`. Each file is self-contained and dated.

## Current best

**43.97 tok/s median decode (steady-state tg_3s: 47.5 - 48.4 tok/s)** on varied text (NPRED=400-600, `bench/prompt2.txt`),
rebased onto upstream `master` (`f7591a6`, 127 commits, tags through `b12190` / `v0.9.0-dev`),
with GPU draft sampling offload (`common/speculative.cpp`), single-synchronization speculative sampling (PR #30196), KV-only graphs for MTP draft catch-up (`ba3e503`), reduced draft vocabulary LM head (`6ec6635`, `--spec-draft-vocab /mnt/ssd/models/draft-vocab-32k.json`),
CUB hardware radix sort on sm_72 (`1f33695`), the `mmvq.cu` dispatch patch, the 64-register launch bounds on the IQ3_S MoE kernel, the dense
rows-per-block / carveout / `small_k` changes, the `concat_non_cont` launch geometry,
`--spec-draft-n-max 6 --spec-draft-p-min 0.50`, `-ub 32 -b 32`, q8_0 KV, backend sampling `-bs` (`--backend-sampling`),
and decoupled TokenGate prefill ubatch (`TG_UBATCH=1024` default) with auto-spanning (`--tokengate-auto`), MoE MMQ enablement (`mmq.cu`), and FlashAttention approximation (`--tokengate-fa`).
Draft acceptance: **0.96806 - 0.97546**, mean length: **5.53 - 5.75**, and **0 changed-size graph reallocs**.

**Prefill & TTFT (updated 2026-11-08):**
MoE MMQ enablement (`mmq.cu:500`) eliminating the sm_72 CPU expert routing stall and Phase 2 FlashAttention (`--tokengate-fa`) elevates TokenGate prefill to:
- **22.1k prompt (`bench/prompt-22k.txt`, 22,128 tokens):**
  - **Internal prefill throughput: 2,025.0 tok/s** (10,926.8 ms prompt processing time)
  - **Client TTFT: 11.15 s (2,011.5 tok/s wire rate)**
- **9.6k prompt (`bench/prompt-8k.txt`, 9,563 tokens):**
  - **Internal prefill throughput: 2,070.6 tok/s** (4,618.0 ms prompt processing time)
  - **Client TTFT: 4.79 s (1,998.9 tok/s wire rate)**
- **Accuracy guarantee mode ($K=2000, W=2$):**
  - Document prefill **1,715 tok/s**, TTFT **5.81 s** at 9.6k tokens with **100% exact cryptographic passkey retrieval (`BLUE-VELVET-99`)**.
- **Startup Warm-up:** Automated 1-token graph warm-up integrated into `bench/run-best.sh` eliminates the 4.97 s cold capture tax.
- **261k Context Verification:** Full **262,144 context** (`-c 262144`) verified with `q8_0` KV cache, leaving **4.4 GB of free RAM headroom** on Jetson AGX Xavier.

**Absolute prefill levels are not stable between server loads, so TTFT is quoted as a range
(2026-11-05).** With a byte-identical binary and identical flags at n_prompt 9,563, the same
prompt has read **92.0, 79.5 and 76.5 tok/s** across server loads - TTFT 104-125 s. Storage
(a cold page cache costs 5.1%), the board clocks (GPU pinned at 1,377 MHz, MAXN, host idle) and
the machine's pure-load DRAM rate (93.1 GB/s, unchanged to 0.1% between the 92.0 and 76.5 states)
have each been measured and eliminated, so only same-server-load interleaved A/B deltas are
quotable; see [2026-11-05-prefill-page-cache.md](2026-11-05-prefill-page-cache.md) section 3c.
The documented TTFT at 9,563 tokens is **120.2 s conservative, 104 s in a good server load**. Campaign is in `TODO.md`.

The validated launch command, build recipe and expected numbers live in
[`../KNOWN-GOOD.md`](../KNOWN-GOOD.md); `../bench/run-best.sh` runs it directly.
Against the no-speculation baseline on the same prompt that margin is **+102%** (18.32 tok/s, the
post-2026-11-03 figure); the +107% quoted in older notes pairs the draft with the 16.64 tok/s
baseline that predates the dense-MMVQ work, and the two should not be mixed.

**MTP-free profile (measured 2026-11-05, corrected 16:45 - a separate goal, it does not supersede
the line above).** On 2026-11-05 the instruction changed to "maximize without having to stay
MTP-compatible", which opens every knob the drafter used to veto. The ceiling without the MTP head
is **27.86 tok/s plain decode** (`-bs`) with `Q4KM-all-q4k.gguf` (four measured requant steps on
top of Q4_K_M, +25.2% decode for +1.67% perplexity) at `-ub 2048`, **23.75 on an 8.8k context**,
**23.18 with the DFlash sidecar on 8.8k of code** (plain Q4_K_M), and **215.8 tok/s prefill / TTFT
53.3 s at 11,484 tokens** - against the MTP configuration's 36.93 tok/s and 120.2 s. Decode and
TTFT are separable: `-ub` no longer touches decode at all, and prefill is flat across the four
quant files (214.3-220.9). **`-ub 2048` is the widest width that measures reproducibly**: 3072 and 4096 read
32% and 72% spreads over identical loads, so every prefill figure published at 3072 before 16:45
on 2026-11-05 (215.0 / 173.3 / 225.5) is superseded. See
[2026-11-05-mtp-free-campaign.md](2026-11-05-mtp-free-campaign.md) sections 18-23.

Runners-up and context are in [2026-11-01-decode-speed-tuning.md](2026-11-01-decode-speed-tuning.md).
The 2026-11-02 sweep re-tested KV type, batching, speculation depth, quantization, build
flags and context depth; **none of them beat this configuration**
([2026-11-02-todo-sweep.md](2026-11-02-todo-sweep.md)). A follow-up audit closed the last 28
untested server flags and measured the hardware ceiling: this board delivers **109.7 GB/s** to
a GPU read kernel, while a second concurrent stream *lowers* aggregate throughput
(31.20 -> 24.64), so decode is latency-bound rather than bandwidth-bound
([2026-11-02-bandwidth-and-flag-audit.md](2026-11-02-bandwidth-and-flag-audit.md)).

**Corrected 2026-11-02:** the "decode uses ~12% of peak bandwidth" figure that stood here has
been **retracted**. It counted only streamed weights and ignored re-reads in the verify pass.
Counting exact tensor bytes, a batch-1 pass moves 2.34 GB in ~60 ms (39 GB/s) and a verify pass
4.18 GB in ~118 ms (35 GB/s) against the 110 GB/s ceiling - so the real figure is **32-35% of
peak**, not 12%. This does not restore bandwidth as a lever; it makes the remaining headroom
smaller than the retracted number suggested.
([2026-11-02-per-op-profile.md](2026-11-02-per-op-profile.md))

The old headline **25.39 tok/s** is superseded: it was measured on a repetitive prompt, which
inflates MTP throughput by 40-60%. See the methodology section below.

## Measurement conventions (read before comparing any two numbers)

Two artifacts were discovered late and invalidated several earlier conclusions. They are
documented in full in
[2026-11-01-decode-speed-tuning.md](2026-11-01-decode-speed-tuning.md#two-benchmark-artifacts-that-inverted-earlier-conclusions).

1. **Repetitive prompts inflate MTP by 40-60%.** The head predicts repeated text almost
   perfectly. Always use varied prose (`bench/prompt2.txt`).
2. **Short measurement windows understate steady state by ~15%.** Headline numbers are measured
   over 400 generated tokens. 128-token numbers are only good for ranking.
3. **Prefill needs its own harness and its own protocol (2026-11-04).** `bench/one.sh` sends
   `cache_prompt: true`, so reps 2+ evaluate only the tokens past the cached prefix; its PP column
   is an artefact and no prefill comparison may be made from it. `bench/prefill.sh` sends
   `cache_prompt: false` on every rep, `n_predict 1`, streams and clocks the first chunk on the
   client, and records the server's `prompt_n`. Prefill is reproducible to **0.14%** over 3 reps,
   so it needs fewer repeats than decode - and it is a different kernel set (MMQ, not MMVQ), so a
   decode result never transfers to it.

Unless stated otherwise, numbers quoted in these files are one server load per config, greedy
sampling, EOS ignored to force equal output length, and the median of measured repetitions.

**Graph state caveat:** llama.cpp checks `getenv("GGML_CUDA_DISABLE_GRAPHS") != nullptr`, so
setting it to `0` *disables* graphs. Any older entry that calls `=0` "graphs enabled" is
mislabelled; those runs were graph-disabled. To enable graphs, unset the variable entirely
(`env -u GGML_CUDA_DISABLE_GRAPHS`).
