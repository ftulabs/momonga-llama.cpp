# `output.weight` Q6_K -> Q5_K: -44.2%, and the drafter needs bit-identical numerics

Date: 2026-11-03. Machine: Jetson AGX Xavier, Volta sm_72. Library md5
`5c129aaee1a8ec8c3d7fda1a14d3e7d6` (unchanged - this is a weights experiment, not a code change).
Control measured in the same session: **34.82 tok/s** (34.10 / 34.83 / 35.16 / 34.82 / 34.70),
acceptance 0.96657, mean_len 5.68.

## 1. Why this was the most promising lever left

The pass budget (`./2026-11-03-decode-pass-budget.md`) puts the lm_head at 41.1 ms of
163.4 ms, and `output.weight` is Q6_K at 417,177,600 bytes, read **7 times per pass** - once at
7 columns for the verify, six times at 1 column for the MTP drafts. That is 2.92 GB per pass, more
than the entire main forward reads. Q5_K is 176 bytes per 256 elements against Q6_K's 210, so the
same tensor becomes 349,634,560 bytes: **-16.2%, -470 MB per pass**.

Critically, this is the only weight change that does **not** touch expert routing. `ffn_gate_inp`
is untouched, so the trap that closed the f32 router experiment
(`./2026-11-03-mmwq-launch-params.md` section 5) should not apply.

## 2. Prediction, written before the run, and it was wrong

`/tmp/pred-lmhead-q5k.txt`: predicted **~36.3 tok/s (+4.3%)** and acceptance >= 0.94, on the
reasoning that the six 1-column draft calls are bandwidth-bound at 80 GB/s (72% of the 111 GB/s
ceiling) so their time should scale with bytes, and that changing the output head moves the
target and the drafter *together*.

Measured **19.43 tok/s, -44.2%**, acceptance **0.63603**. Both halves wrong, and the second one is
the interesting failure.

## 3. Results

| | control (Q6_K) | Q5_K lm_head |
|---|---:|---:|
| tok/s, median of 5 | **34.82** | **19.43** (-44.2%) |
| all reps | 34.10 / 34.83 / 35.16 / 34.82 / 34.70 | 18.86 / 19.43 / 19.45 / 19.19 / 21.17 |
| draft acceptance, median | **0.96657** | **0.63603** |
| all reps | 0.96657 (bit-stable) | 0.63060 / 0.71616 / 0.63603 / 0.62642 / 0.69283 |
| mean_len | 5.68 | 2.20 (2.14 / 2.25 / 2.20 / 2.15 / 2.56) |

The file was verified before it was measured (`AGENTS.md` section 3 rule 7): 753 tensors in both
files, **only** `output.weight` differs in type, and 8 sampled tensors were hashed byte-identical
between old and new - `token_embd`, `blk.2.ffn_up_exps`, `blk.40.ffn_down_exps`, two
`ffn_gate_inp` routers, two `ssm_out`, one norm. The requant itself is sound: RMS 0.020716 ->
0.020711 and cosine 0.99938 on a 4000-row sample.

## 4. Mechanism: the drafter needs bit-identical numerics, not merely similar ones

A cosine of 0.99938 on the output head should be imperceptible. It is not, because the MTP
drafter shares this tensor. Acceptance 0.967 -> 0.636 means the drafter's token and the target's
token disagree most of the time, and throughput is `mean_len / pass_latency`: mean_len 5.68 ->
2.20 is -61%, only partly offset by the shorter pass.

**This is the fourth independent way to reach acceptance ~0.63-0.72, and the pattern is now the
finding.** The three requanted expert builds gave 0.64-0.93; the f32 router change gave 0.67717;
the deleted jusko Volta fork gave 0.678; this gives 0.636. Four different mechanisms - different
expert weights, different routing, a different codebase, and now a different output head - all
land in the same band, while the untouched control reproduces 0.96657 bit-for-bit on every run
ever logged. The model's speculation only works when the drafter and the target are numerically
*identical*, not close. Anything that perturbs either side by one ulp decouples them.

That makes "small enough to be safe" the wrong way to reason about weight changes here. A change
either touches no numbers or it is a different model as far as the drafter is concerned.

**Consequence: Frontier 6 is closed, and with it the whole "make a weight smaller" family** - q4_k,
q5_k, `--override-tensor` to 4-bit on any per-pass tensor, uniform requants. The one exception
worth keeping is a **bit-preserving** repack (padded block layout), which changes where the numbers
sit but not what they are, so it should leave acceptance untouched. That is now the only
weight-adjacent avenue left, worth ~+2%.

## 5. What this experiment could not resolve

Pass latency fell from 163.1 ms to 113.2 ms (-31%, computed as `mean_len / throughput`), which is
in the direction the byte saving predicts. But it cannot be attributed to Q5_K: with mean_len 2.20
the draft chains are shorter, so the verify runs narrower than 7 columns and is cheaper for that
reason alone. Separating "fewer bytes" from "narrower verify" needs the kernel measured at fixed
geometry - `opbench` at K=2048, n=248320, ncols 1 and 7, q6_K against q5_K. Not worth doing here,
because the end-to-end result rejects the change regardless of which explanation holds.

## 6. Artefacts

- `Cyber-Tiel-Coder-35B-A3B-MTP-UD-IQ4_XS-lmheadq5k.gguf` - the rejected file (18,052,391,232 B).
- `bench/requant-one-tensor.cpp` - single-tensor requant through ggml's own `ggml_quantize_chunk`,
  so the blocks are exactly what the in-repo quantizer produces. Reusable.
- `bench/build-lmhead-q5k.py` - rebuilds the GGUF with one tensor replaced; resumable tail copy.
  Records the constraint that cost a false start: **a tensor cannot be shrunk in place**.
  `gguf.cpp` requires every tensor offset to equal the cumulative padded size, so there is no hole
  to leave and the loader fails with `gguf_init_from_reader: failed to read tensor data`.
- `bench/text-sample.sh` - greedy sample for eyeballing quality; unused here because the change
  was rejected on acceptance first.
